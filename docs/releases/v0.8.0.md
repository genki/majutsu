# majutsu v0.8.0

## 概要

master／slave構成の耐久性モデルを変更したminor releaseである。cluster masterはS3 relayではなく
データ保持専用nodeとなり、slaveの通常クラッシュ保全をslave／masterの二重化で成立させる。
S3/GCSは非同期の二次バックアップとして扱う。

## 主な変更

- cluster protocolをv2へ更新した。
- master-local storeと永続backend queueを追加した。
- slaveへのACKを、S3 PUT完了後ではなくmaster-localのatomic writeとfsync完了後に返す。
- GET／Range GET／Exists／Listはmaster-localを優先し、移行前履歴だけS3へfallbackする。
- slave同期用のmaster-local専用LISTとsync cache v3により、upgrade後の初回syncで
  現在参照されるobjectをmasterへ再複製する。
- S3転送を既定1時間または1 GiB thresholdの非同期workerへ分離した。
- mutable refをkey単位でcoalesceし、content、metadata、refの順に二次転送する。
- master／slave双方へ自律retryとjitter付きbackoffを追加した。
- slave watch daemonが未試行queueとremote ACK前のdurable journalを自動検出し、live rootを
  再走査しない単発queue-only syncで自律的に収束させる。
- journal payloadの取得失敗をrecord単位で分離し、読めるrecordの送達を継続する。進捗がない
  retryは30秒backoffし、cluster watch起動時も恒久的なpendingを待ち続けない。
- host別token、host-bound認証、自prefixだけを変更できるACLを追加した。
- protocol v2 capability handshakeでframe、batch、payload、operation上限を接続前に照合する。
- `mj cluster status`、`mj cluster metrics`、`mj cluster flush`を追加した。
- master-local DELETEを7日間安全保持する永続retention／GCを追加した。
- flush単位のLIST dedupe、foreground優先concurrency gate、`Content-MD5`付きS3 multi-object
  deleteを追加した。
- clone中にjournal retention GCが並行しても、一覧取得後に消えたrecordを安全にskipする。
- master容量、S3 lag／retry、quota拒否、slaveから見たmaster停止の通知hookを追加した。
- cluster master roleの`mj watch`をデータ保持server専用にし、`snapshot`／`sync`を拒否する。
- cluster未設定時は従来のstandalone動作を維持する。

## 互換性

protocol v1とv2のmixed operationは非対応であり、接続時にfail-fastする。失敗時もslave upload
queueは削除されない。slave daemonを停止し、master、slaveの順で全nodeを更新する。

## 継続計測

- 初期full seed完了後の安定した24時間について、S3 request数と追従遅延を継続計測する。
- 定常区間でも新規immutable objectのPUT数が目標を超える場合だけ、二次backend専用pack形式を
  次版で検討する。restore formatを複雑化するため、実測前には導入しない。

## 実機確認

- macOSの`mba22`をdata-holder master、Linuxの`vagrant`とWindowsの`win-vr`をslaveとして
  protocol v2へ更新した。
- master停止中にslave queueが保持され、master再起動後に手動syncなしで再送を再開した。
- backend queue保持中のmaster process再起動後も、master-local storeとqueueが維持された。
- Windows slaveはqueue 0、journal pending 0、current 115/115 missing 0へ収束した。既存の
  `.ssh/known_hosts` ACLに由来するroot warningはデータ取得権限の問題として残した。
- master roleで`snapshot`／`sync`が拒否され、`status`／`health`がdata-holder状態を表示した。
- GCS実環境で2件のDELETEを1回のPOSTへまとめ、個別DELETE 0、backend failure 0でqueue 0まで
  flushした。
- backend flushと並行したclone／quick fsck／restore比較が成功し、foreground処理が枯渇しない
  ことを確認した。
